# macOS allocation tags: source meaning and a bounded counterexample

#19768 reports roughly 14 GB under application-specific tag 14 and 3,582 MB under tag 16. Those labels help distinguish mapped regions, but do not identify the allocating Orca function or divide memory cleanly into native objects versus JavaScript-backed buffers.

## Exact reported-version source

Electron **43.4.1** pins Chromium **150.0.7871.224** and Node **24.18.1**; its release lists V8 **15.0.245.28**. The references and fetched source hashes are in [sources.json](./sources.json). No full upstream source is included. [Electron DEPS](https://github.com/electron/electron/blob/v43.4.1/DEPS), [release versions](https://releases.electronjs.org/release/v43.4.1).

- Apple's application-specific labels 14 and 16 correspond to numeric VM tags **253** and **255**. Chromium names these `kPartitionAlloc` and `kV8`, and its POSIX allocator passes the chosen value through `VM_MAKE_TAG`. These are region tags, not ownership backtraces. [Apple definitions](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/mach/vm_statistics.h), [Chromium tags](https://github.com/chromium/chromium/blob/150.0.7871.224/base/allocator/partition_allocator/src/partition_alloc/page_allocator.h), [mapping code](https://github.com/chromium/chromium/blob/150.0.7871.224/base/allocator/partition_allocator/src/partition_alloc/page_allocator_internals_posix.h).
- **Browser main and `ELECTRON_RUN_AS_NODE` both construct `JavascriptEnvironment`.** That installs gin's ArrayBuffer allocator. RUN_AS_NODE skips the browser's embedded Node startup snapshot; it does not switch this isolate to ordinary Node's default ArrayBuffer allocator. [Browser startup](https://github.com/electron/electron/blob/v43.4.1/shell/browser/electron_browser_main_parts.cc), [Node entry](https://github.com/electron/electron/blob/v43.4.1/shell/app/node_main.cc), [environment initialization](https://github.com/electron/electron/blob/v43.4.1/shell/browser/javascript_environment.cc).
- **gin ArrayBuffer allocation uses PartitionAlloc inside the V8 sandbox.** Chromium reserves its configurable pool through the sandbox address space, then places the ArrayBuffer partition there. V8's Darwin/POSIX mapping uses tag 255; allocating inside an existing reservation can merely change permissions. Consequently, a logically PartitionAlloc-owned buffer can occupy tag-255 pages. [gin allocator](https://github.com/chromium/chromium/blob/150.0.7871.224/gin/array_buffer.cc), [pool placement](https://github.com/chromium/chromium/blob/150.0.7871.224/gin/v8_initializer.cc), [V8 reservation allocation](https://github.com/v8/v8/blob/15.0.245.28/src/base/platform/platform-posix.cc).
- **Reuse can change the tag.** PartitionAlloc's direct-map release accepts the configurable pool and calls `UnreserveAndDecommit`. That operation remaps pages with tag 253 using `MAP_FIXED`; later reuse can therefore allocate buffers in tag-253 mappings. This is a source-traced route, not a measurement of its contribution to #19768. [Direct-map release](https://github.com/chromium/chromium/blob/150.0.7871.224/base/allocator/partition_allocator/src/partition_alloc/partition_page.cc), [pool decommit](https://github.com/chromium/chromium/blob/150.0.7871.224/base/allocator/partition_allocator/src/partition_alloc/address_pool_manager.cc), [tagged remapping](https://github.com/chromium/chromium/blob/150.0.7871.224/base/allocator/partition_allocator/src/partition_alloc/page_allocator_internals_posix.h).
- **Node Buffer APIs have multiple backing routes.** Ordinary ArrayBuffers and zero-filled `Buffer.alloc(size)` use the isolate allocator. Electron's sandbox patch routes unsafe Buffer backing, including nonzero-fill allocations, through V8's default sandbox allocator; native Buffer copy/new paths also use isolate-backed stores. Thus neither a Buffer API name nor the process mode alone determines its VM tag. [Node Buffer implementation](https://github.com/nodejs/node/blob/v24.18.1/lib/buffer.js), [native Buffer paths](https://github.com/nodejs/node/blob/v24.18.1/src/node_buffer.cc), [Electron sandbox patch](https://github.com/electron/electron/blob/v43.4.1/patches/node/support_v8_sandboxed_pointers.patch), [V8 default allocator](https://github.com/v8/v8/blob/15.0.245.28/src/api/api.cc).
- **`arrayBuffers: 0` does not establish absence of buffer memory.** Node's metric returns zero when its own allocator pointer is absent. Electron creates browser IsolateData with that pointer null; its Node entry also omits the optional allocator. The separate `external` metric comes from V8. [Electron IsolateData setup](https://github.com/electron/electron/blob/v43.4.1/shell/common/node_bindings.cc), [Node memory accounting](https://github.com/nodejs/node/blob/v24.18.1/src/node_process_methods.cc).

## Installed-binary counterexample

```sh
ORCA_BACKGROUND_LAUNCH=1 node docs/audits/macos-allocation-tags/probe.cjs
```

The macOS-only probe uses the installed Electron in RUN_AS_NODE mode, opens no application windows, retains bounded allocations, records process metrics and `/usr/bin/vmmap -summary`, then terminates each child. It compares fresh allocations with allocation/free/GC cycles followed by a retained allocation. The recorded binary is **Electron 43.7.0**, Chromium 150.0.7871.250, Node 24.21.0, on macOS 26.6.2. This is neither the exact reported Electron version nor the browser-main execution mode.

In the recorded fresh-allocation controls, ordinary JS arrays add about 32 MiB of `heapUsed` and tag-255 **DIRTY** memory. Sixty-four touched 1 MiB `Uint8Array` or nonzero-filled Buffer allocations add about 64 MiB of `external` memory and tag-255 DIRTY memory. `arrayBuffers` remains zero. After three allocation/free/GC cycles, retained Uint8Array data instead raises tag-253 DIRTY from about 4 MiB to 69 MiB while tag 255 remains about 4 MiB. Reused Buffer allocations appear mainly under `VM_ALLOCATE`, demonstrating another backing route. These observations refute a fixed native-versus-JavaScript meaning for either tag, as well as “zero arrayBuffers means no buffer allocation.” [Recorded observations](./results.json).

Compare the exact `Memory Tag 253` and `Memory Tag 255` **DIRTY** columns, and include `VM_ALLOCATE` when examining the reuse controls. `dirtyDeltaBytes` converts vmmap's rounded size strings, so it estimates byte deltas rather than measuring exact byte counts. The much larger virtual/reserved sizes, whole-process RSS and physical footprint answer different questions. Allocation/reuse history, build flags and allocation size can change the relationship. The reuse control supports the source-traced retagging explanation; it does not measure how much of #19768 followed that route.

## Plausible main-process producers, without attribution

- **IPC serialization and pending message ownership:** Electron's serializer grows a native `std::vector<uint8_t>` and moves it into the outgoing message. Orca's [renderer notification sender](../../../src/main/window/runtime-renderer-notification-sender.ts) reaches that boundary. A live serialized copy can outlast its input's JS call. [Exact serializer](https://github.com/electron/electron/blob/v43.4.1/shell/common/v8_util.cc).
- **Image capture, encoding and byte copies:** Orca's [snapshot capture](../../../src/main/browser/browser-screencast-snapshot-capture.ts) obtains a NativeImage, encodes PNG/JPEG and constructs a Uint8Array. Native bitmap/encoder storage and ArrayBuffer storage are distinct allocations. [Electron image conversion](https://github.com/electron/electron/blob/v43.4.1/shell/common/api/electron_api_native_image.cc).
- **Buffer/typed-array producers:** terminal models, file/stream reads and protocol assembly remain relevant allocation classes; JavaScript ownership can retain backing stores outside `heapUsed`. The tags alone cannot select or exclude these paths.

This narrows interpretation of the report. It supplies no allocation stack, retaining path, browser-main measurement, historical-binary reproduction or causal attribution for the large incident.
